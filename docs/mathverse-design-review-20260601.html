P0致命问题 — 涉及资金、未授权成本与身份伪造

1. 微信支付回调无签名验证 —— 任何人可免费开通会员

app/routes/pay.py:94 wechat_callback

回调直接信任请求体里的 out_trade_no，查到订单就把 status=active、user.tier=plan。没有验签、没有金额核对、没有幂等。外网任意 POST 即可白嫖会员。prepay 返回的 paySign:"MOCK_SIGN" 也说明支付从未真正接通。
接入微信支付 v3 平台证书验签（Wechatpay-Signature 头）+ 校验回调金额与本地订单一致 + 以 order_id 做幂等（已 active 直接返回 SUCCESS）。验签失败一律拒绝。

2. step-explain / similar 无鉴权、无配额、直连 DeepSeek

app/routes/solve.py:98、:126

这两个端点没有任何 Depends(get_*_user)，未登录即可调用，且每次都直接花钱调 api.deepseek.com。等于把你的 API Key 暴露成一个公开的、无限量的免费 LLM 代理 —— 成本 DoS。此外无 try/except，DeepSeek 返回错误结构时 data["choices"][0] 直接 KeyError → 500。
加 get_current_user 依赖并纳入每日配额；包裹异常转 502/503；给 httpx 调用统一封装（见 P2-13，复用 agent_client 的降级思路）。

3. 付费到期永不降级 —— 会员永久有效

app/routes/pay.py:112 写入 tier_expires_at，全仓无任何读取/降级逻辑

配额判断只看 user.tier == "free"。一旦付费，tier 被设为 monthly/quarterly/yearly 后再也不会回到 free，tier_expires_at 形同虚设。
在鉴权依赖里集中判定有效期：is_paid = tier!='free' and tier_expires_at > now()，过期即视为 free（或起一个定时任务/登录时惰性降级）。配额判断改用此函数，别再裸比字符串。

4. CORS 通配 + 携带凭证，配置自相矛盾

app/main.py:15 allow_origins=["*"] 且 allow_credentials=True

按 CORS 规范，credentials=True 时 origin 不能是 *，浏览器会拒绝该响应；同时生产环境全量放开来源也是风险。
用环境变量配置白名单 origin 列表（小程序后端其实不依赖 CORS，H5 上线时再精确配置）。开发与生产分离。

5. JWT 密钥默认值可预测且无启动校验

app/config.py:6 jwt_secret = "change-me-in-production"

若部署时漏配 JWT_SECRET，服务会用公开的默认串静默启动，任何人可据此签发任意 user_id 的 access token，越权登录任意账号。
启动时断言生产环境密钥非默认值（lifespan 内校验，缺失则 fail-fast）；密钥长度 ≥32 字节。

P1功能性 Bug — 主流程会失败或数据失真

6. /api/auth/refresh 参数形态与前端不匹配，刷新必失败

后端 auth.py:115 async def refresh_token(refresh_token: str) ← 裸 str = query 参数；前端 api.ts:31 把它放在 POST body

FastAPI 会把它当作必填 query 参数，前端发 JSON body → 422，access token 过期后无法续期，用户 15 分钟后被强制掉线。现有测试只验证了 token 解码，没真正打这个端点，所以漏过。
用 Pydantic 模型接收 body（class RefreshReq(BaseModel): refresh_token: str），并补一条真实调用该端点的测试。

7. OAuth state 存在进程内存字典 + 多 worker

auth.py:21 _state_store: dict；compose/设计为 2 workers

wechat_login 在 worker A 写入 state，wechat_callback 可能落到 worker B，_state_store.pop(state) 取不到 → "Invalid state"。重启亦丢失。登录会概率性失败。
state 存 Redis（带 TTL），或先用单 worker 过渡。生产上 OAuth/支付/限流状态都不该放进程内存。

8. quick_solve 不计配额、不归档 —— 免费配额可绕过

solve.py:88

配额逻辑只在 deep_solve 里，quick 既不查 quota 也不写 QuestionArchive。免费用户改打 quick 即无限解题；同时 quick 解的题不进存档/热力图。
把配额校验与归档抽成共用函数，deep/quick 都走（quick 可单独计数权重）。

9. StudyPlan.plan_date 用 DateTime 列存 date 对象

models/all.py:81 定义 DateTime；me.py:238/255 用 date.today() 查询和插入

SQLite 弱类型下今天碰巧能跑，但 UNIQUE(user_id, plan_date) 与 == 比较依赖字符串格式一致，跨时区/迁移 PG 后会出现"每次都新建当天计划"或唯一约束冲突。
列类型改 Date，统一用 date 进出。

10. streak_days / last_active_at 永远为 0

全仓无写入点（仅 model 定义与读取）

首页连续打卡、/api/me/streak 的 streak_days 恒为 0；热力图 count 来自 QuestionArchive 尚可，但"连续天数"是死值。
在解题/复习成功后更新 last_active_at，按"昨天是否活跃"递增/重置 streak_days。抽到一个 touch_activity(user) 工具。

11. 多学段知识图谱缺失，全部回退到考研图谱

learn.py:21 找不到 {stage}.json 即 fallback kaoyan-college.json；目录下确实只有这一个文件

设计承诺 primary/junior/senior/college 多套图谱，实际小学初中高中请求都返回考研内容；radar 与 plan_generator 也硬编码只认 gs/xd/gl 前缀（考研三科）。
短期：在文档与 UI 明确"当前仅大学/考研"；中期：补齐各学段 JSON，radar 分组改为读图谱里的 subject 而非前缀硬编码。

P2架构债 — 设计与实现脱节

12. 三处"设计中的能力"是死代码 / 从未接线

  • middleware/content_filter.py —— filter_text 全仓无人调用，且 SENSITIVE_PATTERNS 是占位符（"敏感词示例1"）。设计宣称"双向敏感词过滤"。
  • services/latex_renderer.py —— 注释自承"Phase 2 实现"，/api/render/latex 端点不存在。
  • AnalyticsEvent 表 —— 无任何写入，"行为埋点/业务看板"无数据来源。
二选一：要么接线（解题入口/AI 输出过敏感词、关键动作写埋点），要么从设计文档移除以免误导。建议至少把 content_filter 接到 solve 入口（合规红线）。

13. prompts/ 目录缺失 —— 讲课/模板调用发空 system prompt

agent_client.py:118 读 ../../prompts，不存在则 template=""

generate_lecture、chat_with_template 当前等于"无系统提示词裸调 Chat"，讲课质量无法保证。CLAUDE.md 已记录此坑。
补建 prompts/lecture/*.txt 等模板；模板缺失时记 warning 日志而非静默空串。

14. DB 会话样板重复 + 鉴权多一次往返 + detached 对象

几乎每个路由手写 db = SessionLocal(); try/finally db.close()；auth_middleware.get_current_user 单独开 session 取完即关

get_current_user 返回的是会话已关闭的 detached User，路由里又各开一个 session —— 每请求至少 2 次连接获取，且若某天访问到惰性属性会 DetachedInstanceError。
引入 get_db() FastAPI 依赖（yield + finally），鉴权与路由共用同一 session；User 不脱管。可减约一半样板。

15. SQLite + 多 worker + 写并发 → database is locked

SQLite 单写者，2 个 uvicorn worker 同时写（解题归档、错题、计划）会偶发锁库。MVP 可接受，但要有意识。
短期：开启 WAL（PRAGMA journal_mode=WAL）+ busy_timeout，或先单 worker；增长期按设计切 PostgreSQL（ORM 已就绪，主要补迁移）。

16. 降级策略未实现

设计 §2.3："DeepTutor 不可用→DeepSeek 直调降级"；实际 solve.py:56 直接抛 503

熔断打开后用户得到的是硬错误，而非设计承诺的降级解答。
在 AgentUnavailableError 捕获处 fallback 到 DeepSeek 直调（已有 key 与调用范式）；或明确把"降级"从设计中降级为 P3。

17. score / plan_generator 逻辑可简化且语义偏差

  • score.py:30-35 每道题 random.choice(kp_list) 随机抽知识点，与"按知识点掌握度估分"的语义不符；elif 里二次 random() 的部分给分逻辑也偏经验值。
  • plan_generator.py:36-40 排序键 -(diff if mastery<0.3 else -diff) 反直觉，难维护（Karpathy：能压成更直白的就重写）。
估分按题型映射到对应知识点子集抽样；排序键拆成清晰的 (mastery, -difficulty, freq_rank) 元组并加注释。

一句话结论
骨架与分层是健康的，但在对外上线前，P0 的支付与鉴权漏洞必须先堵（当前任何人可白嫖会员、可免费烧你的 LLM 额度、可伪造任意用户身份）。其次 P1 的 refresh/OAuth/配额三处会让真实用户主流程随机失败。设计文档与实现的"承诺差"（过滤/渲染/埋点/多学段/降级）应在文档里诚实标注阶段，避免后续误判已完成。
