DeepTutor 高并发优化 · 上线手册

Rollout Runbook · 2026-06-02 · 配套 docs/deeptutor-high-concurrency-optimization-20260602.html · PR #2
核心前提：一切皆 env 开关，默认 = 现状。 这套优化没有「大爆炸式切换」。每个能力由一个环境变量门控，不设就是当前行为。所以上线 = 逐个拧开关 + 每步一个验证门 + 随时可回滚（关掉 env 即回默认）。本手册给出安全顺序。顺序很重要：必须先有共享状态(P1) + 去亲和(P3a) 才能开多 worker，否则面 A 的 turn 会被误杀。

开关速查

开关组件默认作用何时拧
DEEPTUTOR_PG_DSNDeepTutor未设会话/turn/事件落共享 Postgres（面 A+面 B）；同时启用 P3a 去亲和Stage 2

安全上线顺序

Stage 0 · 换镜像，全开关默认 → 验证无回归基线
构建打补丁镜像并部署，所有开关保持默认（WEB_CONCURRENCY=1、不设 DEEPTUTOR_PG_DSN、DEEPTUTOR_ROLE=all）。此时行为应与上线前完全一致，只是启动器换成了 gunicorn(-w 1)。 
docker build -t <reg>/deeptutor-patched:<tag> deeptutor-patch/   # patch.py 全程 assert，构建若过=锚点没漂移
# 部署后看日志应有: "patched ok: ... backend launcher -> gunicorn(...)"
验证门：现有功能全绿（解题/拍照/讲解）；DeepTutor 启动日志正常；/ 健康检查 200。
回滚：换回上游镜像 ghcr.io/hkuds/deeptutor:latest（仅丢失本次拍照补丁）。
Stage 1 · 起 Postgres → 跑平价测试地基
起一个 测试用 Postgres（独立于生产数据），跑契约/平价测试，确认 Postgres store 与 SQLite store 行为一致、P3a 回归通过。此步不碰生产。 
# 在打补丁镜像内（或上游 checkout + 装依赖）：
pip install pytest pytest-asyncio asyncpg
DEEPTUTOR_PG_DSN=postgresql://u:p@pg-test:5432/dt_test \
  pytest deeptutor-patch/tests/test_session_store_parity.py -v
验证门：SQLite + Postgres 两个后端的所有断言全过；test_p3_tail_foreign_turn_streams_without_failing 通过（证明跨进程订阅不再误杀 turn）。
回滚：无影响（纯测试）。不过门则停下排查，不要进 Stage 2。
Stage 2 · 单副本开 DEEPTUTOR_PG_DSN → 验证状态外置切状态
给单个 DeepTutor 副本设 DEEPTUTOR_PG_DSN（指向生产 Postgres），WEB_CONCURRENCY 仍为 1。会话/turn/事件从此落 PG。
  • 面 A：发起一次解题，确认 sessions/turns/turn_events 表有数据；中途断线重连能续上。
  • 面 B：/api/v1/chat 解题，确认会话进 PG（不再写本地 JSON）。
验证门：新会话出现在 PG；重连/历史正常；无 PostgresSessionStore requires DEEPTUTOR_PG_DSN 之类报错。
回滚：去掉 DEEPTUTOR_PG_DSN → 立即回到 SQLite/JSON（旧会话不迁移，可接受）。
Stage 3 · 调大 WEB_CONCURRENCY → 压测找拐点加并发
现在 PG(P1) + 去亲和(P3a) 都就位，开多 worker 才安全。逐步 WEB_CONCURRENCY=2 → 4 → 8，每档用 load-tests/ 压测。 
for v in 10 25 50 100 200; do TARGET=ws://127.0.0.1:8001 VUS=$v k6 run load-tests/deeptutor-chat-ws.js; done
重点看：不是单条延迟（被 LLM 吐字速度主导），而是 拐点处的 VU 数、turn_error 率、有无 turn 被误杀/会话损坏。
验证门：加 worker 后吞吐上升、error 率平稳；无「turn failed」异常；PG 无写冲突报错。
回滚：WEB_CONCURRENCY=1。若多 worker 下出现 turn 误杀，说明 P3a 未生效（检查 DEEPTUTOR_PG_DSN 是否设上），回退并排查。
Stage 4 · 起 LiteLLM 网关 → 改 model_catalog 指向它接网关
起 gateway/（litellm + redis），把 DeepTutor model_catalog.json 的 LLM/embedding/vision base_url 改成 http://litellm:4000、api_key 用网关 master key。真实 key 只配在网关。
务必先核对 model_catalog.json 真实 schema（见 k8s/README 警告）：在能跑的实例上 cat data/user/settings/model_catalog.json，按真实字段名改，否则 LLM 调用会超时。
验证门：解题仍正常；curl http://localhost:4000/health -H "Authorization: Bearer $KEY" 健康；网关日志看到多 key 轮询；故意压高看是否优雅 429 而非账户被封。
回滚：把 base_url 改回 https://api.deepseek.com/v1 + 直连 key。
Stage 5 · 多副本 (k8s) + ROLE 拆分横向扩
填好 k8s/ 占位符，kubectl apply -k k8s/。deeptutor-web 多副本(ROLE=web) + deeptutor-bot 单副本(ROLE=bot)。因 P3a 去亲和，ingress 无需 session 亲和。
  • 验证跨副本流式：A 副本发起的 turn，从 B 副本订阅能正常流（P3a 生效）。
  • 验证 bot 只启一次（web 副本日志应有 "skipping TutorBot auto-start"）。
  • HPA：加压看 deeptutor-web 自动扩；万级建议换在飞-turn 自定义指标（CPU 会低估 IO 密集负载）。
验证门：加副本线性提升吞吐；跨副本订阅不丢/不误杀；bot 不重复；超 LLM 配额时表现为排队/429 而非雪崩。
回滚：缩回单副本；或 kubectl rollout undo。

上线时要盯的信号

信号健康报警含义
turn_error / WS 异常关闭率平稳低位多 worker 误杀 turn（P3a/PG 没配对）
PG 写延迟 / 连接池等待低事件日志写入压力 → 加池/批量/读副本
网关 429 / key cooldown偶发账户配额见顶 → 加账户 key（真实天花板，见设计文档 §5）
mathverse-api 入场背压拒绝数低DeepTutor 容量不足 → 扩 deeptutor-web
deeptutor-web 副本数 (HPA)随负载顶到 maxReplicas → 调高上限/加节点

Go / No-Go 总检查单

  • ☐ Stage 0：打补丁镜像无回归
  • ☐ Stage 1：平价 + P3a 回归测试全绿
  • ☐ Stage 2：会话确实落 PG、重连正常
  • ☐ Stage 3：多 worker 下吞吐升、error 平、无误杀
  • ☐ Stage 4：网关接入、model_catalog schema 已核对、优雅 429
  • ☐ Stage 5：跨副本订阅 OK、bot 单实例、HPA 生效
未包含（低优先级残留，按需再做）：
  • 输出转对象存储（main.py:258）—— 仅当用到 DeepTutor 的 visualize/animation 产物时需要（多副本下一副本产物另一副本取不到）。MathVerse 不经 DeepTutor 用产物，故可缓。
  • P3b：Redis pub/sub 替代 P3a 的轮询（更低延迟/更省 DB）+ 跨进程 submit_user_reply/cancel 转发。仅影响 ask_user 交互流；MathVerse 不用。

每个 Stage 的回滚都是「关掉对应 env / 换回镜像」，因为全部改动零默认变化。遇到不过门，停在该 Stage 排查，不要叠加下一步。
