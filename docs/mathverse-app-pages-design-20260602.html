API 绑定（含本次唯一后端改动）

API 缺口与决定：现有 POST /api/me/score/estimate 要求前端传 knowledge_points（每个 KP→掌握度 的完整字典），但没有任何 GET 暴露这个原始字典（/progress/radar 只给 3 个学科聚合值，无法反推）。
决定（已确认）：后端新增 GET /api/me/score/estimate，直接从 LearningProgress 读掌握度 + user.exam_mode，复用现有 estimate_score()。前端零负担。仿照 plan/today 自取 DB 数据的写法。
请求返回（沿用 estimate_score 的结构）
GET /api/me/score/estimate?exam_mode=math-1
（默认取 user.exam_mode）		{estimated_score, score_range, pass_probability, weak_areas[]}

交互规格

  • 顶部 exam_mode 三段选择器（数学一/二/三），切换重新请求。默认 = 用户 exam_mode（无则 math-1）。
  • 环形仪表显示 estimated_score（/150），下方 score_range。
  • 及格概率卡显示 pass_probability%。
  • weak_areas[] 返回的是 kp_id → 前端用知识图谱把 id 映射成中文名（learn store 已加载 KG，可复用；映射不到则原样显示 id）。
  • 无学习数据时（掌握度全空）→ 后端返回 estimated_score:0，前端显示「先去做几道题，攒点数据再估分」。
估分是 2000 次蒙特卡洛的粗略代理（后端 score.py 已注明），页面文案需弱化精确性、强调「趋势参考」。

API 绑定

动作请求 / 返回
当前身份GET /api/pay/subscription → {tier, tier_expires_at, active_subscription}
套餐列表GET /api/pay/plans → plans:[{id, name, amount, days}]（amount 单位分，÷100 显示）
下单POST /api/pay/wechat/prepay body {plan:"quarterly"} → {order_id, amount, prepay_params{timeStamp,nonceStr,package,signType,paySign}}
拉起支付Taro.requestPayment(prepay_params)

支付流程

  1. 进入页 → 并行拉 subscription + plans，渲染当前身份与三张套餐卡（季卡默认高亮「超值」）。
  2. 选套餐 → 底部按钮文案随选中项变化。
  3. 点支付 → POST prepay 拿 prepay_params → Taro.requestPayment。
  4. 支付成功回调由后端 /wechat/callback 处理（激活订阅、升级 tier）→ 前端 requestPayment success 后重新拉 subscription 刷新身份。
真实支付的前置条件（非本次代码能解决）：服务器 .env 的 WECHAT_* 当前为空，prepay 返回的 paySign 是 MOCK_SIGN → Taro.requestPayment 会被微信拒绝。
本页策略：完整搭好真实流程；requestPayment fail 时优雅提示「支付功能即将开放」，不崩。配齐微信商户密钥后零改前端即可真实付费。
