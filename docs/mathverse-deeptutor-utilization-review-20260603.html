2. 值得复议的真实欠用点（按 ROI 排序）

① enable_web_search：全链路接通却被全局开关锁死　本轮已解决

该参数原只受全局配置 deeptutor_enable_web_search（默认 False）控制，从未暴露为请求级选项。 已修复：deep_solve / quick_solve / deep_solve_stream 新增 enable_web_search 覆盖参数， 语义为 全局floor OR 本次opt-in（只能开不能关，默认零变化）；SolveRequest.use_web 与 /ws/solve init 的 use_web 透传到 /deep · /quick · /ws/solve。测试 test_deep_solve_web_search_opt_in_threads_through。 agent_client.py · solve.py · solve_ws.py
（前端 UI 开关刻意未加——对纯应试数学价值低、有幻觉风险，留作产品决策；API 焊死已解除。）

② 原生 question/generate 缺位 → 出题降级为提示词工程

generate_quiz 用 chat WS + JSON 提示块重新实现出题（agent_client.py:257-270）， 绕过了引擎原生的题目生成契约与 RAG 接地。后果：题目无法"基于上传教材语料"出题、结构不保证、解析靠正则兜底（无 JSON 则返回空列表）。 文档已承认此为延期项（"needs real教材 corpus"）——属外部语料阻塞，非纯工程缺口。

③ turn 运行时只用了约 60%

  • capability 子集：仅 4 个，引擎 capability 注册表（deeptutor.capabilities.request_contracts）更大；deep_research、quiz 等未透出。
  • tools 从不传：turn.start_turn 支持 tools= 选择/约束工具集，tutor 路由（tutor.py:97）从不传 → 无法做"只用计算器/只用绘图"这类受控导师。
  • regenerate　本轮已解决：/ws/tutor 现支持 init {type:"regenerate", session_id} → 走 conn.regenerate(scoped_session)；前端抽出共享 openTurnSocket 助手 + 会话栏"重答"按钮。测试 test_tutor_regenerate_reruns_session / _requires_session。tutor.py · stores/tutor.ts

④ attachments：文档输入面缺失

见上表。对已经做了 AI 教材（book）和笔记本（notebook）的产品定位，"把一份 PDF 试卷/讲义喂给导师"是顺理成章的下一步，目前无路可走。

⑤ capabilities 发现端点未用 → 前后端能力清单硬编码漂移风险

低优先，但属技术债：引擎升级能力时前端不会自动跟随。

3. 有意且正确的"不用"（无需整改）

  • co_writer / tutorbot——全局态，多租户下会串户，弃用决策正确。
  • multi-user / sessions CRUD——MathVerse 自管鉴权与会话归档，复用引擎的反而引入冲突。
  • question-notebook——被自研 MistakeNotebook + FSRS 取代，这正是 MathVerse 相对 DeepTutor 的差异化价值（中国应试域）。
  • 引擎管理面（settings/system/plugins/agent-config）——理应内网隔离，不暴露。

4. 最大风险：用了的能力≠验证过的能力

"利用度"有两个维度，第二个维度目前几乎为零。
按 CLAUDE.md / PR #2 约定，PR #15 新接的全部 DeepTutor 能力——vision/solve、question/judge、turn 运行时（含 ask_user 事件名）、 RAG 知识库上传与检索、visualize、以及高并发补丁的 PG/Redis/F1-F2-G1 修复——都只做了静态验证（锚点唯一、能 import、能 compile）， 从未对真实 DeepTutor 引擎跑过端到端。线上 kuangyebar.cn 真正验证可用的，仍只有 PR #1 的 chat→deep/quick 一条路。

也就是说：账面上"接入了 75%"，可活引擎验证过的可能不到 20%。合并 PR #15 前的真机验证 pass 是第一优先，远高于去补上面那些欠用点。
