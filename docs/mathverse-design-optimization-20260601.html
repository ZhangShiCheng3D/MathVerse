数界 MathVerse · 设计系统性优化方案

以白标开源引擎 DeepTutor 的真实能力为基准，重审并优化 MathVerse 的产品与架构设计 · 2026-06-01

本方案的依据
此前的产品/技术设计文档基于对 DeepTutor 能力的假设书写。本次通过 gh 直接核实了 HKUDS/DeepTutor 仓库 deeptutor/api/main.py 的真实路由注册，以及官方对其架构的描述。结论是：当前 MathVerse 与 DeepTutor 的集成契约几乎完全不成立，同时 DeepTutor 已自带多项 MathVerse 正在重复自建的能力。下面据此给出系统性优化。

已核实 路由前缀、WebSocket 中心化交互、鉴权依赖、自带能力清单，以及解题/拍照/出题/仿题/判分各端点的真实路径与 WS 消息信封（见附录，读自 router 源码）。 待确认 仅剩 WS 流中事件级字段（如 mode 取值、event 名、增量分片格式）—— 需对照运行实例 /docs 与抓包最终敲定。

三、被忽视的高价值能力 → 用户需求映射

这些是"白标引擎已经有、但 MathVerse 设计没用上、且直接命中用户需求"的能力。

Book Engine → "学习"入口的体验质变

当前"讲解 = 一段 AI 文本 + 一个 Manim 视频"。Book Engine 能把一个知识点编译成交互式学习单元：定义块 + 概念图（依赖关系可视化，正好替代手搓的知识地图局部）+ 例题块 + 即时闪卡 + 随堂测验 + 动画，全部由引擎生成与校验。用户需求"我要学这个知识点"从"读一段话"升级为"走一遍可交互的微课"。

unified_ws 流式 → 解题的"过程感"与可中断

6-Agent 深度解题耗时数十秒。阻塞 POST 下用户只能干等转圈。改走统一 WebSocket：实时回传"正在分析题型→正在求解→正在校验"的过程事件，命中产品设计里"会话即记录""零摩擦"的原则，也避免 90s 超时悬崖。MathVerse 侧 nginx 已预留 /ws，只需做 WS 中继与协议翻译。

vision_solver → 拍照解题不必自建

产品设计把"拍照"列为第一优先输入，却要靠自建 MathPix 集成。引擎自带 vision_solver，直接复用即可省一条外部依赖链与其成本/限流风险。

memory(L1/L2/L3) → 真正的"懂你"

品牌人格写着"了解你的学习"。仅靠 LearningProgress 的掌握度数字做不到。引擎三层记忆（按日轨迹 / 带引用的事实 / 跨场景画像）可让讲解与解题携带"你上次卡在洛必达条件""你偏好几何直觉"等上下文。建议：结构化掌握度仍自管（估分/计划需要），对话上下文交给引擎记忆。

tutorbot → "AI 学伴"从口号到落地

"三位一体"的学伴角色目前是空的。tutorbot 是持久、多实例、可多渠道在场的 Agent，可承载"每日学伴"，并对接微信服务号模板消息做复习提醒/打卡推送——正好接上 FSRS 调度与留存设计。

四、修订后的架构原则与集成层（AgentClient v2）

  1. 契约对齐：所有调用走 /api/v1，并版本锁定；启动时拉一次 /api/v1/capabilities 做能力探测与契约自检。
  2. 长任务流式：solve / question / research / visualize 经 unified_ws；MathVerse 提供自己的 /ws，做"引擎事件流 → 小程序事件流"的中继与裁剪。REST 仅用于 knowledge / dashboard / settings 等取数配置。
  3. 鉴权直通：DeepTutor 端点默认需鉴权。两个选项——(a) 现阶段维持 ENABLE_AUTH=false + 严格内网隔离（DeepTutor/Qdrant 不可外达）；(b) 开启引擎鉴权，BFF 持服务令牌调用。建议先 (a)，多租户时切 (b)。
  4. 薄适配、不分叉：agent_client 保持薄封装，不 fork DeepTutor，让上游更新可平滑流入；用契约测试（对照 /docs 的 schema）守住边界。
  5. 降级语义重定义：现有"DeepTutor 不可用→DeepSeek 直调"在新模型下应明确为：流式中断/超时→提示重试或转快速模式，而非伪造一个简化解（避免给出未经校验的数学结论）。

八、风险

  • 上游 API 演进：DeepTutor 活跃迭代，端点可能变。对策：版本锁定 + 契约测试 + 薄适配，不分叉。
  • 鉴权与暴露面：引擎端点默认需鉴权而 docker 关了它——务必确保 DeepTutor/Qdrant 仅内网可达，否则等于开放无鉴权 AI 算力。
  • 流式与成本：research/visualize/animator 昂贵且耗时；freemium 经济模型需把这些划入付费档，并对 WS 会话设时长/并发上限。
  • 数学正确性：复用引擎的 verification 链优于自建简化解；降级路径不应输出未校验结论。
  • 字段级未知：本方案核实到路由与交互模型层；上线前需对照运行实例 /docs 落实每个端点的请求/响应 schema。
一句话结论
MathVerse 的产品定位与业务分层是对的，但对引擎能力的假设是错的：既把引擎已有的（拍照解题、判分、出题、知识库、记忆、Book、学伴）重复自建，又用错了集成契约（路径/流式/鉴权三重错配）。系统性优化的主线是——把数学智能与内容生产彻底下沉到 DeepTutor 的真实接口（/api/v1 + unified_ws），MathVerse 专注微信渠道、变现与合规这层不可替代的业务壁垒。第一步且唯一阻塞项：P0 契约验证。

AgentClient v2 改写蓝本

  • 从 httpx-POST 客户端改为 WS 中继：BFF 与 DeepTutor 维持 WebSocket（/api/v1/chat、/vision/solve、/question/*、/quiz-judge），把引擎事件流翻译成小程序自有 /ws 的精简事件（nginx 已留 /ws + 86400s 读超时）。
  • 解题：连 /api/v1/chat 发 {message, mode:"solve", session_id}；逐片转发"分析/求解/校验"事件；结束后落库归档（沿用现有 QuestionArchive / record_attempt）。
  • 拍照：连 /vision/solve 发 image_base64。删除 MathPix 自建计划。
  • 判分：连 /quiz-judge，移除上一轮自建的 /exercise/grade DeepSeek 裸调（判分结果仍接回 record_attempt 驱动掌握度）。
  • 仿题：/question/mimic 取代自建 similar 端点。
  • 会话：用引擎 session_id 贯穿一次解题/学习会话，落实产品设计"会话即记录"。
  • 鉴权：现阶段 ENABLE_AUTH=false + 内网隔离；上多租户时为 WS 握手注入服务令牌（ws_require_auth）。
新发现散文 vs 结构化：chat WS 流回的是散文答案（stream/result 文本），并非产品设计假设的结构化 {steps[], knowledge_points[]}。三层展示需提示引擎按 JSON 返回再解析（在 message 内约定 schema），或接受散文并前端排版。此项为采用 WS 后的必做决策。
已落地本仓库已新增 services/deeptutor_ws.py（chat/vision/judge 三个已核实端点的 WS 客户端）+ tests/test_deeptutor_ws.py（用进程内真实 WS 服务器跑契约测试），并将 agent_client.deep_solve/quick_solve 切到 chat WS（散文答案，steps 暂空，circuit breaker 保留）。出题/讲解待 question/* 事件 schema 确认后迁移。
