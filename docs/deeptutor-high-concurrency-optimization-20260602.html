DeepTutor 高并发系统性优化方案

目标：从「单机单进程、面向单用户/小团队」演进到 万级（10k+）并发 · 可横向扩展 · 2026-06-02
依据：直接读取 HKUDS/DeepTutor main 分支真实源码（非假设）。所有结论附 file:line 证据。
一句话结论。 DeepTutor 当前是一个 单进程、单 worker、带大量进程内单例与本地磁盘状态 的 FastAPI 应用，它的并发模型是「为本地/单用户而生」。要达到万级并发，瓶颈不在 CPU/GPU，而在三处：(1) 进程内状态（turn 执行注册表、JSON 文件会话、内存事件总线）阻止安全地多进程/多副本；(2) 本地磁盘状态（SQLite 会话库、JSON 会话文件、本地输出目录）阻止无状态副本共享；(3) 外部 LLM 吞吐天花板（DeepSeek/DashScope 账户级限流）才是真正的物理上限。优化主线 = 无状态化 App 层 → 外置状态到共享数据层 → 在 LLM 网关做分布式限流/多 key 负载均衡 → 边缘做 WS 亲和路由 + 多副本自动扩缩。

0. 核查方法与范围

本方案不基于对 DeepTutor 的假设，而是逐文件读取其真实源码后撰写。仓库结构：deeptutor/ 包共 599 个 Python 文件，核心并发相关子系统为 api/（FastAPI 入口 + 25 个 router）、services/session/（会话/turn 存储）、services/llm/（35 文件，LLM 客户端 + 限流）、services/rag/（LlamaIndex + qdrant）、core/ + events/（流与事件总线）、runtime/（启动编排）。已精读的关键文件均在下文以 文件名:行号 标注。

注：DeepTutor 在本项目中以上游镜像 ghcr.io/hkuds/deeptutor 形式使用，仅通过 deeptutor-patch/patch.py 构建期覆盖少量文件。本方案默认沿用「fork + 构建期覆盖」交付，既能改内部、又能跟随上游（见 §6）。

1. 两个并发面（关键区分）

DeepTutor 对外暴露 两套语义不同的 WebSocket 流，并发约束完全不同。把它们混为一谈会导致优化方向错误。

维度面 A：统一 WS /api/v1/ws面 B：直连流 /api/v1/chat 等
谁在用 DeepTutor 自带 Next.js 前端 MathVerse 本项目（deeptutor_ws.py 连的就是它，含 /vision/solve、/question/judge）
执行模型 turn-runtime：后台 task 跑 turn，事件持久化到 store，支持订阅/重连/取消 unified_ws.py:71-110 在同一条 WS 连接内、同一进程里直接把 ChatAgent 的流转发出去 chat.py:191-221
会话存储 SessionStoreProtocol → 默认 SQLite 本地库 / 可选 PocketBase protocol.py:14 遗留 JSON 文件 SessionManager（整文件读-改-写，无锁）base_session_manager.py:97-109
跨进程订阅 致命 非属主进程订阅会把 turn 判为孤儿并 标记 failed turn_runtime.py:933-945 无此问题 整个 turn 在一条连接内完成，不跨进程
横向扩展难点 必须 会话亲和 或 共享事件总线 只需 外置 JSON 文件状态 + 多 worker/多副本
对本项目的含义：MathVerse 走的「面 B」反而更容易扩——没有跨进程亲和约束。优先把面 B 打到万级（无状态会话 + 多副本 + LLM 网关），面 A（带重连的高级 UX）作为后续。下文路线图据此排序。

3. 头号架构约束：turn 执行是进程本地的

这是整份方案最重要的一条，决定横向扩展策略。subscribe_turn 的逻辑（turn_runtime.py:879-945）：

  1. 先从 共享 store 回放历史事件（get_turn_events(after_seq)）—— 这部分跨进程可用。
  2. 若本进程的 _executions 里有该 turn 的执行体，挂一个内存订阅队列做实时推流。
  3. 若本进程没有该执行体（turn 跑在另一进程/副本），且 store 里 turn 仍是 running → _fail_orphan_running_turn 直接把它 标记 failed turn_runtime.py:933-945, 573-587。
后果：在「面 A」(/api/v1/ws) 上，任何「在非属主进程上订阅一个运行中 turn」的行为会 误杀该 turn。这意味着 —— 哪怕只是同一容器内开 2 个 uvicorn worker —— 一旦某条 WS 落到另一个 worker，就会破坏正在跑的 turn。

因此面 A 的横向扩展有两条路：

路线 A1：会话亲和（最小改动）路线 A2：共享事件总线（彻底）
做法 每容器 单 worker；LB 按 session_id 一致性哈希把同一会话的所有 WS 路由到同一副本；靠加副本扩容 turn 执行体把事件发到 Redis pub/sub（keyed by turn_id）；任意副本的 subscribe_turn = store 回放 + Redis 订阅；属主用租约/心跳判活而非「是否在我进程」
改动量小（不改 DeepTutor 代码，靠边缘路由）中-大（改 turn_runtime 推流与订阅）
多核利用每容器 1 核有效 → 靠 k8s 一节点多容器补可多 worker，充分利用多核
故障转移副本挂 → 该会话进行中的 turn 丢失，需重发turn 可由其他副本接管订阅，体验更平滑
建议先做 A1 把面 A 拉到可用万级稳定期再上 A2

面 B（MathVerse 实际路径）不受此约束：整个 turn 在一条连接内一个进程跑完，不存在跨进程订阅。所以面 B 可以直接多 worker + 多副本，唯一要解的是 B1（开 workers）+ B3（外置 JSON 会话）。

5. 容量模型：10k 并发到底要多少机器

「并发」必须定义清楚。对 LLM 服务，真正的并发单位是 「在飞 turn」（正在流式产出的解题会话），而非「TCP 连接」。一条 turn 的生命周期 80% 时间在 等 LLM 吐 token（IO 等待），CPU 占用低。

量级含义主导约束
10k 在线连接1 万个小程序同时挂着 WS，但大多 idle仅靠 FD/内存，单层多 worker 即可扛（每连接 ~几十KB）
10k 在飞 turn1 万个解题 同时在流式产出外部 LLM 吞吐 才是天花板，不是 DeepTutor 本身

估算（以 10k 在飞 turn 为目标）

  • App 层：异步 IO 下，单 worker 可同时持有数百条流式 turn（受事件循环调度 + 每 turn token 处理 CPU 限制，保守按 ~250/worker）。10000 / 250 ≈ 40 个 worker 进程。每节点 8 核跑 6-8 worker → 约 6 台 8 核机器（加冗余 8-10 台）。这部分很便宜。
  • 状态层：PostgreSQL 单主 + 读副本，事件日志写入是主要负载（每 turn 数十条 event）。万级在飞 ≈ 数万 event/s 写入 —— 需要 批量写 + 连接池 + 可能分区表；单台高配 PG 可达数万 TPS，配 PgBouncer。
  • 推理层（真正的瓶颈与成本）：10k 在飞 turn 同时向 DeepSeek 流式 = 10k 并发上游请求 + 巨量 token 吞吐。DeepSeek 账户级并发/RPM/TPM 限额远低于此。必须：(a) 多账户/多 key 负载均衡；(b) 全局分布式限流 + 排队；(c) 超出即背压（429/排队），而非硬打上游被封。若要真正自持万级、低延迟、可控成本 → 评估 自托管 vLLM 推理集群（GPU）承载主力流量，外部 API 作溢出。
  • qdrant：检索是 turn 内的少数几次调用，读多写少；分片+副本的 qdrant 集群可达数万 QPS。
必须向上管理的预期：「DeepTutor 支持万级并发」在工程上是可达的，但 万级 在飞解题 的成本与上限由外部 LLM 决定，不由 DeepTutor 代码决定。DeepTutor 侧的优化目标应明确为：(1) 不再有进程内/本地状态阻止水平扩展；(2) 在 LLM 网关做优雅背压，过载时排队/降级而非雪崩；(3) App/状态层能线性加副本。把「10k」锚定在「10k 在线连接 + 在飞解题受控排队」是务实且可交付的。

7. MathVerse 集成层改造（mathverse-api）

MathVerse 当前对每个请求新建一条 WS、无连接池、无队列（deeptutor_ws.py:61 websockets.connect per call；agent_client.py 仅有进程内熔断器）。万级下需要：

  • 连接复用/池化：对 DeepTutor LB 维护长连接池，避免每次握手开销与连接风暴。
  • 有界并发 + 入场队列：MathVerse 侧设全局在飞上限（与 DeepTutor 容量匹配），超出排队，再超出快速 429 + Retry-After（已有 nginx limit_req，需对齐到容量模型）。
  • 熔断器跨副本：当前 CircuitBreaker 是进程内（agent_client.py:64-89），多副本下各自计数；可接受，但建议把「DeepTutor 不可用」信号放 Redis 共享，避免每个副本各自试探。
  • 超时分层：deep_solve 90s 对万级排队场景偏短；区分「排队等待超时」与「流式产出超时」，给前端「排队中」状态而非直接失败。
  • 降级语义：保持「不可用→提示重试/快速模式」，不伪造未校验的数学解（沿用现有设计文档结论）。

8. 分阶段落地路线图

按「先让 MathVerse 实际路径（面 B）可扩，再上面 A 高级能力」排序。每阶段带可验证判定标准。

P0 · 解除单进程枷锁 + 压测基线奠基
  • 改启动为 gunicorn + N uvicorn worker（覆盖 start-backend.sh）。注意：开 worker 前必须确认面 A 的亲和（否则 turn 被误杀）—— 故 P0 先只对 面 B 开 worker，或单容器单 worker + 多副本。
  • 搭压测工具（k6/locust 模拟 WS 解题），建立 当前单实例 的并发-延迟-错误率基线曲线（找到拐点）。
判定：有一张「并发 vs P95 延迟 vs 错误率」基线图；多 worker 下面 B 解题正确、无 JSON 会话损坏（先验证 B3 是否在并发下真的损坏）。
P1 · 状态外置（PostgreSQL）关键路径
  • 实现 PostgresSessionStore(SessionStoreProtocol)，env 切换 store 后端；面 A turn/事件日志入 PG。
  • 面 B 的 JSON 会话改走共享 store（或最小化：单会话单文件 + 文件锁，消除整文件读-改-写竞态）。
  • 引入连接池（asyncpg + PgBouncer）。
判定：两个副本指向同一 PG，会话/历史在副本间一致可见；并发写无丢更新（对比测试）；本地磁盘不再持有会话状态。
P2 · 多副本 + LLM 网关 + 分布式限流扩展层
  • 容器化为无状态副本，k8s 部署 + HPA（按在飞 turn/连接数扩缩）；WS-aware ingress。面 A 加 session_id 会话亲和路由（路线 A1）。
  • 上 LLM 网关（多 key/多账户负载均衡 + 全局限流 + 重试/熔断）；DeepTutor base_url 指向它。
  • traffic_control.py 令牌桶后端改 Redis；TutorBot 角色门控；输出转对象存储。
判定：加副本能线性提升吞吐；超过 LLM 配额时表现为 排队/429 优雅背压 而非整体超时雪崩；副本重启不丢他人会话。
P3 · 面 A 去亲和（共享事件总线，可选）体验增强
  • turn 事件经 Redis pub/sub 跨副本分发；订阅 = store 回放 + Redis；属主判活改租约/心跳。
  • 解除「单会话单进程」约束，允许多 worker、平滑故障转移与重连。
判定：客户端中途断线后由 任意 副本重连可继续 turn；多 worker 下 turn 不被误杀。
P4 · 数据层抗压 + qdrant 集群 + 可观测性稳态
  • PG 分区表/读副本/批量写事件；qdrant 分片+副本；全链路 metrics（在飞 turn、队列深度、LLM 等待、限流命中）+ 链路追踪 + 告警。
  • 混沌/容量演练：拔副本、限流上游、慢 LLM，验证背压与恢复。
判定：万级在线连接 + 受控在飞解题下稳定运行 ≥ N 小时，SLO 达标，过载可预测降级。

10. 需要你拍板的决策

  1. 面 A 是否在范围内？ MathVerse 当前只用面 B。若近期不需要 DeepTutor 自带前端的「重连/订阅/取消」高级 UX，可暂缓 P3 和面 A 的亲和复杂度，把火力集中在面 B 的万级（P0-P2 即可达成）。
  2. 推理层策略：纯外部 API（多账户网关）起步，还是同时规划自托管 vLLM 集群？前者快、成本随量线性且受上游限额；后者重、需 GPU，但才能真正自持低延迟万级。
  3. 状态层选型：直接上 PostgreSQL（推荐，为万级而生），还是先用上游已有的 PocketBase（快但本质单节点 SQLite，扛不到万级写）过渡？
  4. 编排平台：上 k8s（HPA/ingress 成熟），还是 docker-compose + 多机手工（轻但扩缩与 WS 亲和要自己搭）？
我的推荐起步切片（若你同意，我下一步就做）：把范围锁定在 面 B 的万级 —— P0（gunicorn 多 worker + 压测基线）→ P1（PostgresSessionStore + 面 B 会话外置）→ P2（无状态副本 + LLM 多 key 网关 + Redis 分布式限流）。 这条线不触碰 turn-runtime 的亲和复杂度，是 MathVerse 实际路径、风险最低、收益最直接的万级路径。面 A（P3）作为后续增量。
