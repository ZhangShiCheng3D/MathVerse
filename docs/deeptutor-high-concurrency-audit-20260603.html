F1【高】非属主副本误杀活着的 turn

问题：P3a 轮询（turn_runtime._tail_foreign_turn）与 P3b Redis（_turn_bus.tail）都让一个不拥有该 turn 的副本在 stale_after=120s 无新事件后把 running 标成 failed——即使属主副本还活着（一次 >120s 无流式输出的慢工具/LLM 调用即触发）。过期判断只看事件活动（updated_at 仅在 append_turn_event 更新），而代码注释承诺的「owner heartbeat/lease (P3b)」从未实现。这正是 P3 本要消灭的跨副本误杀。

修复：引入真正的属主心跳。

  • postgres_store.py：新增 touch_turn(turn_id)——仅当 status='running' 时 bump updated_at。
  • patch.py §9d/§9e：属主在 _run_turn 期间每 30s 跑一次心跳 touch_turn（PG-only，getattr 守卫；finally 取消）。锚点不变，仅替换文本更丰富。

于是 updated_at 成为真实存活信号，120s 过期判断只对真正死掉的属主生效。

G1【高】多副本下 RAG 知识库失效

问题：k8s/deeptutor.yaml 的 web 用 replicas:3 + /app/data 为 per-pod emptyDir。但 DeepTutor 把 RAG 知识库的注册表 kb_config.json、上传原文、磁盘索引存在 /app/data——不在 Postgres（只有 session/turn/event 状态在）、不在 qdrant（只有向量在）。因此副本 A 建的 KB，副本 B 的 kb_config.json 里没有 → /api/kb/list 与 RAG 解题在 B 上 404/落空，非确定性地坏掉。直接影响 PR #15 的 /api/kb/* 与 RAG-grounded 解题。

修复（清单层）：给 web+bot 挂一个 ReadWriteMany 共享卷到 /app/data，所有副本看到同一套知识库；initContainer 改为幂等写入 model_catalog.json。

k8s/data.yaml:      + PersistentVolumeClaim deeptutor-shared-data (RWX)
k8s/deeptutor.yaml: data 卷 emptyDir -> PVC（web+bot）；seed 改 [ -f ] || ... 幂等
前置要求：需要 RWX-capable StorageClass（NFS / CephFS / EFS / Filestore），填 REPLACE_ME_RWX_STORAGECLASS。若集群无 RWX：把所有 KB 写操作 + RAG 请求路由到单一副本，或外置 KB 存储。残留：两副本并发重建同一 KB 索引可能竞争文件——KB 写是低频管理操作，建议串行化。

F2【中】sync→async 桥阻塞 worker 主循环

问题：_pg_session_manager 的 run_coroutine_threadsafe(...).result() 无超时，由 chat.py 在 worker 主事件循环上同步调用。PG 慢/不可达时主循环被无限期阻塞 → 整个 worker 停摆（与高并发目标相悖，单次 PG 抖动变成 worker 吊死）。

修复：result(timeout=DEEPTUTOR_PG_BRIDGE_TIMEOUT，默认30s)，超时抛错（chat.py 转成错误事件，而非吊死 worker）；并给连接池加 command_timeout=30 做纵深防御。
